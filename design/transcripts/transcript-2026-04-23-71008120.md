**Assistant:** Captured. A few important implications to flag:

**Passwords are sacred:**
- Zero-knowledge extends fully to the password manager — encrypted client-side, we never see plaintext, not even for our own suite's login credentials
- This means if a user loses their vault passphrase, that data is unrecoverable — we'll need clear upfront disclosure of that

**All data treated equally:**
- Raw, inferred, metadata, behavioral — same tier rules, same valuation weight per unit of value, same privacy protections
- Simplifies the governance model significantly

**"No third-party apps" but "pull from outside" — there's a tension worth clarifying:**
- Pulling in bank feeds, fitness data, calendars from outside services typically requires connecting to those services' APIs — which means OAuth handshakes and API integrations with those external providers
- That's technically different from embedding a third-party tool *inside* our suite, but it does mean we'd need to build and maintain those connection pipelines
- The alternative is **manual import** — user exports their data from wherever (CSV, JSON) and uploads it into their data hub — no live connection, no third-party dependency, fully user-controlled

**My question:** When you say pull from outside, are you thinking **live connections** (automatic sync with external services) or **manual import** (user-controlled, one-time or scheduled uploads)? Or both?

**User:** I was talking about embedding, but the user should have options on how the data is imported.

What security risks does importing 3rd party through their apps present

**Assistant:** The main risks, organized by type:

**Credential & token risks**
- Live connections require storing OAuth tokens — if our system is breached, attackers gain access to users' external accounts (bank, health, calendar, etc.)
- Tokens often have broader permissions than needed — a read-only bank connection might grant more scope than intended

**Data injection risks**
- Maliciously crafted imported data could exploit our parsers — a corrupt CSV or JSON designed to inject code or break our data pipeline
- Applies to both manual uploads and live connections

**Privacy leakage toward the outside**
- When a user connects to an external service via OAuth, that external service learns they're using our platform — which undermines privacy, especially for higher-tier users
- The external service also sees connection frequency and timing

**Data integrity risks**
- We can't verify the accuracy of externally imported data — users could import manipulated data that skews their algorithms and projections
- A compromised external service could push bad data into a user's data hub

**Re-identification risk**
- Even a Tier 1 zero-knowledge user who imports rich external data creates a fuller profile locally — if their device is compromised, that combined picture is far more revealing than either source alone

**Cascade risk**
- If an external service is breached, the data they synced to us is only as clean as their security

---

**The mitigation that addresses most of these:**
Keep all imported data inside the user's zero-knowledge boundary — we act as a conduit only, never storing external credentials or imported data in plaintext on our servers. OAuth tokens stored encrypted, governed by the same tier rules as everything else.
