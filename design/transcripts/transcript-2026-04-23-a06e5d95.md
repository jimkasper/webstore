**Assistant:** For a platform handling posthumous messages and estate data, "best security" has a few layers worth separating — because the right answer depends on a key architectural choice:

---

**The core tension: Can you (the platform) read user messages?**

Most platforms can. For posthumous letters and sensitive instructions, that's a real risk — data breaches, subpoenas, rogue employees. The gold standard is **zero-knowledge encryption**: the platform stores only ciphertext and can never read user content.

**What that means technically:**
- Messages are encrypted in the browser with a key derived from the user's password (or a separate vault passphrase)
- Only the ciphertext lives on your server
- Posthumous delivery requires cryptographic key management — e.g. Shamir's Secret Sharing, where the key is split across trusted contacts and only reconstructs when enough of them confirm

**The tradeoff:** Zero-knowledge is significantly more complex to build and eliminates features like server-side search of message content. Password recovery also becomes harder (losing the key = losing the content).

---

**The pragmatic high-security baseline (simpler to build):**
- NextAuth with mandatory TOTP/MFA
- All sensitive data encrypted at rest in the DB (column-level encryption)
- TLS everywhere, strict CSP headers
- Audit logs for all access to posthumous content
- No third-party vendors with access to plaintext data (rules out Clerk)
- Rate limiting, brute-force protection

**Assistant:** Zero-knowledge E2E shapes the entire architecture. Here's what that commits you to:

**What happens client-side:**
- User's vault passphrase → PBKDF2 → encryption key (never leaves the browser)
- All messages/instructions encrypted in the browser before upload
- The server only ever sees ciphertext

**Posthumous key delivery with Shamir's Secret Sharing:**
- User's vault key is split into N shares (e.g. 3-of-5)
- Each share is encrypted with a trusted contact's public key
- When triggered, contacts submit their shares → key reconstructs client-side → content decrypts
- Platform never sees the assembled key

**Tech stack this pushes toward:**
- **Next.js** — SSR for non-sensitive UI, client components for all crypto operations
- **PostgreSQL + Prisma** — stores only ciphertext, hashed keys, public keys
- **NextAuth + TOTP** — auth layer (sessions only, totally separate from encryption keys)
- **Web Crypto API** — native browser crypto, no third-party crypto library needed
- **`shamirs-secret-sharing`** — npm lib for key splitting

**What you give up:**
- Server-side search of message content
- Password recovery for vault content (lose passphrase = lose content, unless contacts hold enough shares)
- Simpler debugging/support
